# Cognitive harness audit — scenario evidence matrix

This matrix is the working coverage map for the audit. It describes the modules required by a scenario, not every Python file that may exist in the repository. Conditional/background modules are expected only when their trigger applies. A test pass proves the tested contract, not general semantic quality.

## Evidence labels

- **Live historical**: the report contains a turn/cycle receipt from a Lumina process, but not necessarily the currently running version.
- **Local**: code/tests establish a local contract; no loaded-process claim.
- **Open**: evidence is absent, incomplete, or fails the scenario criterion.
- **Not in path**: an initialized/imported prototype has no active call path and must not be counted as a working capability.

## Module disposition rules

- **Core turn modules** are required for every ordinary human chat turn; their stages must have a turn ID and causal edges.
- **Scenario-conditional modules** (memory, profile, research, affect, action) are required only when the scenario’s semantic route selects them; unrelated questions must not invoke them without reason.
- **Deferred/background modules** may complete after visible delivery; their receipts must retain the originating turn ID and must not veto or rewrite the delivered answer unless a separately defined safety path requires it.
- **Internal-loop modules** are assessed per cycle and cadence. A cadence skip is expected evidence, not a missing execution; an invoked module still needs output and downstream-effect checks.
- **Dormant prototypes** do not count as active capabilities. Example: `GenuineUncertaintyChoice` is instantiated but has no production call site, returns only one alternative, and has unimplemented choice logic.
- The 43-module tick registry is a selected instrumentation manifest, not a claim that all Python files run on each turn. The 279-file static catalog is a source inventory, not evidence of execution.
